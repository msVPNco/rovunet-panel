# Version 2: server acceptance candidate

The version-one GitHub workflow retains its old build recipes and explicitly
refuses a version-two rebuild. Version two is assembled from the exact reviewed
runtime/source bundle, built for both architectures, production-signed locally,
and accepted with those same bytes in the VM before publication. It is not a
replacement build generated by the legacy workflow. The signed manifest binds
the source commit and every shipped asset. Corresponding source/module/crate
archives and component notices accompany the binaries.

Normal complete setup targets 30 unrestricted profiles on Android and Windows,
29 for a time-only account, and six shared-budget paths for accounts with a
traffic limit. Main protocols are first, auxiliary SSH paths next, and all ten
DNS paths last. Display order is not a measured WAN speed ranking.

## Implementation

- Add TLS Vision, XHTTP REALITY, AnyTLS, TUIC, Mieru TCP and Mieru UDP.
- Preserve stable account/profile identity and saved subscription URLs on normal
  updates. Apps refresh the existing subscription; platform capabilities remain
  version-independent integration requirements.
- New accounts bind to durable SQLite accounting. Native finite WS and the five
  Xray bridge profiles share the same account budget. Excluded protocols never
  receive a finite user's credential merely to inflate the profile count.
- Binary traffic units: 25 GB = 25,600 MB = 26,843,545,600 bytes. Unknown historical
  usage remains incomplete, rather than invented zero or exact remaining usage.
- A bounded read-only WAL pool keeps committed policy/metadata reads independent
  of the sole writer. A reproduced writer-connection deadline regression is
  covered by a held-writer test: readers see the last committed state, cannot
  write even if query-only is disabled, and a subsequent reserve still rejects
  a newly committed freeze. No receipt, pending grant or uncertainty is reset.
- Authenticated runtime updates stage and validate all affected files before
  replacement, retain content-addressed old files, and resume journals after
  interruption. Runtime matching remains strict; reviewed dirty builds are
  accepted only by their exact authenticated hashes.
- Compatibility-core revocation for SS2022/Trojan/VLESS Encryption restarts the
  shared core, closing old streams. Other users on that compatibility core may
  briefly reconnect. Native finite relays terminate only the exhausted account.
- Installation now sets required service-group/resolved permissions explicitly,
  including under root umask077. Disabling the resolved stub changes only its
  exact managed resolv.conf symlink, preserving administrator resolver files.
- SQLite backup format2 is age-encrypted by default and contains a hash-verified
  coherent checkpoint. Same-identity forward restoration merges usage upward;
  it preserves current config, periods, credentials and tokens. A changed config
  or missing authority is refused, rather than rolled back from an older file.
- Certificates check/recovery and authenticated public Slipstream certificate
  companions are available. Apps must validate/persist public pins and implement
  explicit changed-pin recovery; no private certificate key is distributed.

## Recorded tests

The acceptance package distinguishes exact executable hashes, source commit,
private lab fixtures and scoped results. It includes:

- All22 Go package suites and go vet. ARM64 backup/network/profile and focused
  ledger tests executed under user-mode emulation, separately from native AMD64.
- A complete signed bootstrap and normal 30/30 install in a clean systemd VM.
  A strict-umask failure was reproduced and fixed; final exact-byte fresh-install
  acceptance is separately recorded and must pass before publication.
- Four account modes30/29/6/6, stable IDs and DNS-last order on both feed types.
- Current six new runtime profiles: 1MiB TCP payload, credential negatives and
  reconnects; UDP payload for TUIC/Mieru; hostname negatives for TLS variants.
- Current native WS through the actual Caddy front: unlimited and finite1MiB
  payload. Finite accounting recorded exactly2MiB, both directions, no pending.
- A trusted synthetic prior-usage fixture left100B: an attempted200B delivered
  exactly100B, overshoot0, close observed0.2899s after attempt, new data rejected,
  and the second user's held stream survived without restarting the service.
  This is a controlled VM result, not an expiry-timer or ISP latency promise.
- Encrypted checkpoint/check/forward restore. Restoring an older checkpoint after
  real finite traffic retained2,097,152 consumed bytes; damaged ciphertext, wrong
  key and stale-config restoration were rejected without rollback.
- Real reboot with changed boot identity:28 running services recovered, config/
  feed items stayed identical, recorded totals did not regress, diagnostics passed.
- Actual DNSTT panel/official invocation, VayDNS native/compatible, Slipstream and
  Naive component payloads. Soar/router/authentication boundaries have separate
  package tests. WAN delegation/client-device qualification is not implied.
- Real Caddy H2/H3 payload and fresh public staging ACME HTTP01/TLS-ALPN01 on an
  owner-authorized VPS; staging trust never entered global public trust stores.
- Patched native TLS/QUIC regressions and sanitizer checks, OpenSSL173 targeted
  tests, Cargo/RustSec and Go advisory scans with recorded official snapshots.
  Clean scans are bounded by that data, not proof that every vulnerability is absent.
- AWG two-peer payload/revocation/recovery on AMD64 and emulated ARM64. Slipstream
  both architectures, wrong/expired pin recovery and reboot have separate receipts.

## Explicit boundaries

Online SQLite checkpoints do not replace fresh-target disaster recovery.
The externally authenticated sealed recovery lane retains single-target and
antirollback requirements. Restoring every runtime, full Caddy storage and all
provider/firewall state on a fresh physical server remains a separate broader
qualification gate; the legacy restore path cannot bypass SQLite authority.

Native WireGuard and TUIC pass controlled runtime payload tests. Observed external
UDP handshake loss does not establish an app defect or guarantee every provider's
reachability. WireGuard and AmneziaWG remain distinct. TLS Vision is an additional
choice alongside compatibility WS, without an unmeasured speed guarantee.

No exact simultaneous-device cap is enabled. Physical Android/macOS/Windows,
physical ARM64, independent/off-site signing custody, every ISP and WARP provider
registration remain separate qualifications. See the capability contract and the
unchanged four broader qualification gates; they are not silently marked verified.
