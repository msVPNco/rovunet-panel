# Rovunet Panel v2.1.0

This release starts from the public v2.0.2 source, commit
`efa697256880b0d2c0b1494513b51f4c72a7735b`, with the owner's requested default
protocol replacements and Free config menu. It does not adopt the private
v2.0.3 source. Version 2.1.0 sorts above both 2.0.2 and 2.0.3 so the ordinary
authenticated Update path can select it once publication is complete.

## Default protocols and ports

| Previous default | Replacement | Fresh-install port | TLS certificate |
| --- | --- | --- | --- |
| WireGuard (`wireguard`) | Shadowsocks 2022 AES-128 (`ss2022-aes128`) | 51820 TCP + UDP | Not required |
| TUIC (`managed-tuic`) | Shadowsocks ChaCha20-Poly1305 (`ss-aead-chacha20`) | 33444 TCP + UDP | Not required |

The exact ciphers are `2022-blake3-aes-128-gcm` and
`chacha20-ietf-poly1305`. The second is classic AEAD ChaCha20, not the different
Shadowsocks 2022 ChaCha20 method. Each user has separate credentials. Both use
the dedicated, authenticated Xray runtime and standard `ss://` feed items.
The existing AES-256 Shadowsocks 2022 core and AmneziaWG are retained.

On upgrade, each selected replacement reuses the old core's saved port and
endpoint, including a custom port. A root-only per-core backup and resumable
journal are written before stopping that core. A new replacement must be
confirmed before the old core is retired. Installation failure restores the
old core where possible and reports any incomplete recovery. Repeating setup
retains successfully created replacement credentials. Disabled or paused old
defaults stay disabled; custom-named cores are not adopted for replacement.

Other core settings and saved ports are retained. Missing cores use the ordered
fixed port choices from 2.0.2, checking the required TCP/UDP listeners; no random
port allocation is introduced. The two intentionally replaced profiles acquire
new IDs and credentials for their new protocols. Existing account IDs, passwords,
periods, known usage and subscription URLs, and unrelated profile IDs and
credentials, must remain intact. Refresh the same saved subscription after a
successful update.

## Free config in the panel

Open **Users → Free config (50 GB / 30 days)**. This creates a marked account
with a shared 50 GiB traffic budget and a 30-day expiry. The account is marked
before its first save; an existing ordinary or archived user is not silently
converted. Failed provisioning can be resumed without resetting its identity
or allowance.

The private candidate is written to `/etc/rovunet/donations/<username>.json`.
**Users → Export Free config for review** retries the export. Only profiles
allowed by the existing finite-account policy are eligible, and export requires
a working, bound, unexhausted accounting ledger. The two new Shadowsocks methods
remain excluded from finite accounts, as does the existing AES-256 method.

This is a server feature and private export. It does not publish donated access,
enable a Free tab in released apps, or establish an app catalog signing key.
The separately reviewed Android/Windows feature needs its own release and
activation. Treat the exported candidate as access credentials.

## Certificates and runtime selection

The public 2.0.2 Slipstream trust-companion route is preserved, including
`/sub/TOKEN.trust.json` for both subscription aliases. Existing TLS validation,
certificate recovery and certificate identities are retained. No insecure TLS
fallback is introduced. The owner's reported connection failures have not been
attributed to certificates by a live client diagnostic.

The known private 2.0.3 preview's `subscription_trust_key_id` field survives
configuration load, save, reload and refresh as compatibility metadata. This
does not implement that preview's separate signed-trust behavior or generate,
rotate or remove its signing key. This release retains the public 2.0.2 trust
body and route; clients that require the private preview's signed trust format
need separate compatibility review. The declared online-update ABI and embedded
SQLite schema match the inspected preview, but the signed acceptance runner
covers public 2.0.2 to 2.1.0, not an exercised upgrade from that private binary.

Managed runtime acquisition is explicitly pinned to the authenticated public
v2.0.2 release, independently of the panel's version. All engine, provenance,
source and notice bytes reused by this release must match its signed manifest
and the existing reviewed runtime pins. A panel version bump must not send
runtime downloads to a nonexistent version or a moving Latest asset.

## Acceptance and publication

Publication requires green CI for the exact source, actual reviewed-Xray TCP
and UDP/lifecycle tests for all three Shadowsocks methods, migration/recovery
tests, complete-setup and finite-account checks, and authenticated installer staging,
update, certificate, backup and accounting gates. The new release workflow
stages an unsigned draft and a concrete signing bundle. The owner's existing
Windows-local production identity signs the manifest; CI does not possess or
replace that private key. Publication verifies every signed asset and checks
that the expected previous Latest is still v2.0.2.

Before asking for a signature, a baseline smoke run exercises the original
signed 2.0.2 installer and the accounting/runtime fixture. After signing, a
separate runner tests the unchanged installer with `--no-run` and the old
panel's actual Update menu against the exact signed candidate. It executes in
private Linux namespaces with simulated systemd; the fresh phase verifies
authenticated staging and pending-setup recovery, not the whole interactive
first-account wizard. The update phase preserves recorded SQLite consumption
and TLS/trust files while replacing only the selected defaults. Its TLS front
and Slipstream services remain administratively inactive, so their preserved
identities do not constitute a live proxy-traffic test.

The checked-in scope describes required acceptance, not a passing receipt.
Actual results belong to the exact source/preparation workflow run and final
signed acceptance receipt. Tests on an isolated runner do not certify every
physical client, ISP, UDP path, provider account or fresh-target recovery.
Those wider boundaries remain in `docs/release-gates.json`.
